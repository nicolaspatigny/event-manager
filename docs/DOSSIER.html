Analyse et expression du besoin

Contexte réel connu

Nicolas Patigny prépare une formation CDA à l’ENI. Ce projet remplace son stage et vise à produire une application full-stack démontrable de gestion d’événements sur un périmètre prévu de deux mois. Aucun nom d’entreprise d’accueil, activité commerciale, effectif, organigramme ou tuteur n’a été communiqué. Le dossier présente donc un contexte de projet pédagogique ; ces informations ne doivent pas être inventées.

Besoin

Centraliser la découverte d’événements, leur publication et les inscriptions, avec des droits adaptés aux participants, organisateurs et administrateurs. Éviter une double inscription, une surcapacité ou la modification des événements d’un tiers.

Acteurs

  • Visiteur : consulter l’agenda, rechercher, lire un événement, créer un compte.
  • Participant (USER) : gérer son profil, s’inscrire, se désinscrire avant le début, consulter ses événements à venir et passés, exporter/supprimer son compte.
  • Organisateur : publier, modifier et annuler ses événements ; voir les noms des inscrits.
  • Administrateur : gérer les comptes/rôles, catégories, tous les événements et les journaux.

L’organisateur ne s’inscrit pas en tant que participant. L’administrateur attribue les rôles ; le formulaire public ne permet jamais de choisir un rôle privilégié.

Décision de stockage

Le PDF prévoyait SQL Server pour le métier et MongoDB pour les journaux. Le porteur a demandé explicitement MongoDB seul. Collections : users, events (inscriptions embarquées), categories, audit. Les relations conceptuelles restent documentées dans le MCD mais ne constituent pas un schéma SQL livré. Faire valider par l’enseignant la couverture de la compétence relationnelle si elle est obligatoire pour la certification. Le projet seul ne prouve pas une compétence SQL exécutée.

Périmètre livré

Authentification JWT et révocation, profil, recherche, événements, inscriptions, administration, tableaux de bord, journaux techniques, export et effacement, interface Angular française, tests HTTP/MongoDB et navigateur, livraison Docker, documentation.

L’annulation d’un événement conserve sa fiche et ses inscriptions afin d’informer les participants. La désinscription retire la réservation ; l’historique affiche les événements passés auxquels l’utilisateur est resté inscrit, pas une archive de chaque réservation annulée. Les journaux conservent temporairement les actions de désinscription.

Limites assumées

Pas de paiement, messagerie, application mobile native, recommandations, e-mails, billets PDF, QR codes, mot de passe oublié ou notifications temps réel. Les places sont bornées à 1 000 pour conserver des documents MongoDB raisonnables. Le MVP n’a pas fait l’objet d’un audit externe ni d’un test de charge de production. Les données de test sont fictives. Les lieux sont des champs structurés au niveau de l’événement, sans référentiel indépendant à administrer.

Conception

Modèle conceptuel de données (indépendant du stockage)

Passage au modèle documentaire

events.registrations est un tableau de { userId, registeredAt }. Le couple conceptuel événement/participant est unique grâce au filtre de mise à jour, pas à un index unique multikey (qui ne garantirait pas l’unicité dans un même document). Les coordonnées du participant ne sont pas recopiées dans les événements. L’API publique retourne une vue sans le tableau ni les identifiants des participants.

Indexes : users.email unique, categories.normalizedName unique, date et organisateur des événements, TTL sur audit.createdAt (90 jours). Les utilisateurs historiques doivent être normalisés avant création de l’index e-mail ; résoudre les collisions explicitement, sans suppression automatique de comptes. Un index unique simple n’est pas insensible à la casse ; c’est la normalisation à chaque écriture qui l’assure.

La suppression d’une catégorie est remplacée par une désactivation pour conserver les références. L’effacement d’un utilisateur retire ses inscriptions et ses données personnelles ; les événements restent avec un identifiant organisateur non résolu et sans coordonnées.

Cas d’utilisation

Architecture

Contrôleurs : adaptation HTTP et validation. Services : règles métier et autorisations. Modèles : documents persistants. DTO/vues : exposition contrôlée. Angular ne décide jamais des permissions réelles : les gardes servent uniquement à l’ergonomie.

Inscription atomique

L’annulation, la réservation et l’édition portent sur le même document. L’édition compare la révision ; les réservations incrémentent cette révision. Pas de lecture puis écriture non protégée pour le dernier siège. Aucun verrou Java en mémoire : la garantie fonctionne sur plusieurs instances d’API. Les tests lancent des requêtes HTTP concurrentes réelles.

Les opérations d’effacement d’un compte touchent plusieurs documents et sont des opérations de maintenance réessayables, pas une transaction globale. Pour une exploitation à fort trafic, prévoir une désactivation préalable et une file de purge contrôlée pour traiter les requêtes déjà en vol, ainsi qu’un rapprochement des références orphelines.

GET /events : q (titre littéral), category (id), location (littéral), from, to (ISO Instant), page (0 par défaut), size (12, maximum 100). scope=public masque les annulés ; mine exige organisateur/admin, registrations exige connexion, admin exige administrateur. La réponse est {items,total,page,size}. Les tableaux admin utilisent la même convention, avec une taille par défaut de 20.

Exemple EventInput :

{"title":"Atelier créatif","description":"Une rencontre ouverte à tous.","startsAt":"2027-06-01T16:00:00Z","location":"Nantes","categoryId":"id-existant","capacity":20,"revision":0}

Les révisions changent après modification, inscription, désinscription ou annulation. Un 409 à l’édition demande de recharger la fiche, pas de répéter aveuglément la requête.

Erreurs : 400 validation, 401 authentification/identifiants, 403 droits, 404 ressource, 409 conflit, 429 limitation au niveau du reverse proxy. Les erreurs métier utilisent application/problem+json avec status et detail. Les validations ajoutent errors. Les réponses inattendues restent gérées par Spring sans stacktrace ni détails internes.

Choix d’authentification

Le JWT est stocké seulement en mémoire du navigateur et expire après une heure. Un rechargement demande une reconnexion. La signature contient l’identifiant du compte et une version ; chaque requête vérifie le compte et sa version en base. Déconnexion, changement de mot de passe et modification des droits invalident les anciens jetons. Les rôles sont relus côté serveur, pas acceptés depuis le navigateur.

CSRF est désactivé parce que l’API utilise uniquement un en-tête Bearer explicitement ajouté ; aucune authentification par cookie n’est utilisée. L’interface et l’API sont de même origine. Les contrôles CORS permissifs ne sont pas activés.

Le reverse proxy Docker limite les tentatives login/inscription (10 requêtes/minute et burst 10 par adresse IP). L’API doit rester sur le réseau interne ; le serveur de développement n’offre pas cette protection. En cas de proxy supplémentaire, configurer l’adresse client de confiance sans accepter aveuglément un X-Forwarded-For utilisateur.

Le contrôle de longueur BCrypt est fait en octets UTF-8 (72 maximum), en plus de la validation en caractères. Le jeton et le hash du mot de passe ne figurent jamais dans les vues ou journaux. L’échec d’audit est signalé dans les logs techniques sans annuler une opération métier déjà réalisée.

Fonctions : rectification du nom, export JSON, effacement du compte et de ses inscriptions, effacement des traces d’audit liées. Pas de marketing ni traceur. Les acteurs sont identifiés par identifiants techniques dans le journal (pseudonymisation, pas anonymisation absolue). Les sauvegardes exigent une politique d’expiration et de réapplication des suppressions après restauration.

Avant un usage réel, l’exploitant doit renseigner : responsable et contact, base légale adaptée (exécution du service pour le compte, intérêt légitime documenté pour les traces ou autre fondement approprié), sous-traitants/hébergement, transferts, registre, durée métier des événements et demandes de droits. Une page de confidentialité et des endpoints ne suffisent pas à établir la conformité RGPD.

Aperçus intégrés

Suivi du démarrage CI

L’utilisateur a signalé un échec d’initialisation du service MongoDB avant exécution des tests GitHub. L’image et l’ancien health check ont démarré correctement en local ; la cause distante exacte n’est donc pas établie sans les logs du conteneur. Le workflow utilise désormais scripts/ci-mongo.sh après checkout : attente de readiness explicite (120 s maximum), erreur si le processus quitte, conservation des logs dans les artefacts des deux jobs et nettoyage en fin de job. Le script et une connexion MongoDB depuis l’hôte ont été validés sur un conteneur isolé local. Ce changement ne transforme pas une panne de base en test réussi ; une nouvelle exécution GitHub reste nécessaire pour confirmer le résultat distant.

Cause confirmée de la panne CI

Les logs fournis par l’utilisateur identifient la cause : l’image MongoDB 8.0 (digest 4a4ab5d4834207389e0d7270fac988e21ffedccecba77991a552f755df229907) refuse de démarrer sur un noyau Linux 6.19 ou ultérieur (MongoDB SERVER-121912). Le label ubuntu-latest migrait vers Ubuntu 26. Les deux jobs sont désormais fixés sur ubuntu-24.04 ; le manifeste officiel runner-images consulté indique un noyau 6.17.0-1022-azure pour cette image. Les actions checkout, setup-java, setup-node, upload-artifact et setup-gradle utilisent des versions avec runtime Node 24 vérifié dans leurs manifestes officiels. Le résultat de la nouvelle exécution GitHub reste à confirmer ; aucune exécution distante réussie n’est affirmée depuis cet environnement.

Livraison, maintenance et exploitation

Configuration

Java 21 complet, Node 24 pour le build, MongoDB 8. Le wrapper Gradle versionne l’outil de build ; npm utilise le lockfile via npm ci. MongoDB seul ; aucun serveur SQL. Le backend reçoit MONGODB_URI, JWT_SECRET, et éventuellement ADMIN_EMAIL/ ADMIN_PASSWORD pour amorcer le premier compte. Le secret JWT doit être aléatoire, privé et d’au moins 32 octets. Aucun secret livré en dur.

Le compte d’amorçage n’est créé que s’il n’existe pas. Ne pas confondre un changement de variable avec une réinitialisation de mot de passe. Après amorçage, retirer le mot de passe admin des variables quand le mode d’exploitation le permet et utiliser le profil pour le changer. Une base existante peut exiger une migration des e-mails : normaliser et résoudre les doublons avant l’index unique.

Docker Compose

Voir le README. docker compose up --build -d, puis vérifier l’API via le proxy et effectuer une vraie connexion. Le ping MongoDB et un processus HTTP ne prouvent pas le fonctionnement métier : créer une catégorie, promouvoir un organisateur, publier et réserver une place. Ne pas ouvrir les ports MongoDB/API au réseau public. Le bind web par défaut est local ; ajouter un reverse proxy TLS administré pour une publication réelle.

docker compose down arrête les conteneurs sans supprimer le volume. Ne pas ajouter -v sur une base à conserver. Une modification des identifiants MongoDB dans .env ne réinitialise pas les utilisateurs d’un volume déjà initialisé : effectuer une rotation avec MongoDB, puis mettre à jour la configuration de l’API.

Sauvegarde / restauration

Depuis un terminal administré, sans journalisation shell des secrets :

mkdir -p backups
# Utilise les variables déjà injectées dans le conteneur, sans les afficher.
docker compose exec -T mongo sh -c 'mongodump --username "$MONGO_INITDB_ROOT_USERNAME" --password "$MONGO_INITDB_ROOT_PASSWORD" --authenticationDatabase admin --db event_manager --archive --gzip' > backups/event-manager.archive.gz
# Restaurer uniquement dans une instance de recette isolée après validation de la cible.
# mongorestore --archive=... --gzip avec les identifiants de cette instance.

Chiffrer les sauvegardes, restreindre l’accès, définir leur durée et tester régulièrement une restauration. Le mot de passe est passé à l’outil interne ; limiter aussi les droits d’accès système au conteneur. La restauration réelle n’est pas attestée sans preuve d’exécution. Réappliquer les demandes d’effacement après une restauration ancienne.

Maintenance

  1. Reproduire un défaut avec un ticket, impact et étapes précis ; exclure les données réelles.
  2. Ajouter un test utile qui échoue, corriger sur une branche, relire la PR.
  3. Exécuter tests API et navigateur, build frontend/backend, revue des dépendances.
  4. Sauvegarder, déployer la nouvelle version, vérifier un parcours métier et les logs.
  5. Revenir à l’image précédente si échec ; ne pas restaurer une base sans analyser les modifications de schéma et les données écrites depuis la livraison.

Surveiller disponibilité, erreurs HTTP, espace disque MongoDB, échecs de login et de journalisation. Le TTL MongoDB est asynchrone ; 90 jours n’est pas une échéance à la seconde près. Les erreurs applicatives n’exposent pas les stacktraces au navigateur.

Limitations opérationnelles

Compose privilégie une démonstration reproductible, pas une infrastructure hautement disponible. Le compte MongoDB root doit être remplacé par un utilisateur applicatif limité avant production. Pas de réplication, monitoring central, sauvegarde automatique, TLS managé ni rotation automatique. Les opérations de purge multi-documents sont à renforcer avant forte concurrence. Le guide décrit les compléments requis sans prétendre les avoir mis en exploitation.

Construction derrière un proxy de confiance

Les Dockerfiles acceptent des secrets BuildKit optionnels : gradle_properties pour les propriétés proxy Gradle, java_truststore pour le magasin de certificats Java, et proxy_ca pour la CA Node. Ils ne sont pas incorporés aux images. Dans un réseau cloud où le nom du proxy n’est pas résolu depuis Docker, fournir aussi un extra_hosts de build avec son adresse actuelle. Ne pas copier de jeton dans un ARG, ne pas désactiver TLS et ne pas désactiver les checksums. Le wrapper vérifie le SHA-256 officiel de sa distribution Gradle, enregistré dans gradle-wrapper.properties.

Compatibilité du noyau avec MongoDB

L’image MongoDB 8.0 utilisée dans cette livraison refuse les noyaux Linux 6.19 ou ultérieurs (voir https://jira.mongodb.org/browse/SERVER-121912). Les conteneurs partagent le noyau hôte : Docker ne contourne pas cette incompatibilité. Utiliser un hôte compatible ou une version MongoDB officiellement corrigée et revalidée. La CI est fixée sur Ubuntu 24.04 pour éviter la migration automatique vers Ubuntu 26.
